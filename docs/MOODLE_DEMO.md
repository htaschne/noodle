# Self-hosted Moodle demonstration

From the repository root, with Docker running, use Docker Compose 2.24.4 or later and OpenSSL. The first start downloads and builds Moodle 4.5.16, installs it in PostgreSQL, provisions the REST account, seeds the course, and runs the first monitoring cycle.

```sh
./scripts/moodle-demo up
./scripts/moodle-demo poll
./scripts/moodle-demo logs --tail=50 monitoring notifications
```

`poll` runs one additional cycle and prints its results. The background worker polls on startup and then hourly. Both use the same RabbitMQ queue and delivery history.

| Open | Sign in |
| --- | --- |
| [Moodle](http://moodle.localhost:18080) | `admin` with `DEMO_MOODLE_ADMIN_PASSWORD`. To see an individual submission, sign in as `alex`, `blair`, or `casey` with `DEMO_MOODLE_STUDENT_PASSWORD`. |
| [RabbitMQ Management](http://localhost:25672) | `noodle_demo` with `RABBITMQ_PASSWORD`. Look for `noodle.reminders` under **Queues and Streams**. |
| [Mailpit](http://localhost:18025) | No login. |

The passwords are generated once and stored in the ignored `.env.moodle-demo-local` file. The service account token is generated by Moodle and mounted read-only into Monitoring. The `.localhost` address works in a browser on the Docker host and resolves to Moodle on the demo's Compose network.

## What to show

The course is **Noodle Demonstration Course**. Deadlines are measured from the first install of that demo instance.

| Assignment | Initial deadline | Expected reminders |
| --- | --- | --- |
| Pending essay | In 2 hours | Alex never started and Casey has a draft. Blair already submitted. |
| Completed worksheet | In 3 hours | None. All three submitted. |
| Future project | In 48 hours | None during the initial demonstration. |
| Expired exercise | 1 hour ago | None. |

For a fresh recording, stop the current demo with `./scripts/moodle-demo down` and select an unused instance. Each instance has its own volumes and credentials. `down` keeps the data and delivery history. Use one instance at a time because the browser ports are fixed.

```sh
export NOODLE_DEMO_INSTANCE=video
./scripts/moodle-demo up --scale monitoring=0
./scripts/moodle-demo stop notifications
./scripts/moodle-demo poll
```

1. Open Moodle and show the four assignments. In **Participants**, filter by the **Student** role to show the three students. As Blair, open **Pending essay** and show **Submitted for grading**. The command output shows three students, two eligible assignments, two skipped assignments, and two published reminders.
2. Open RabbitMQ Management and show **2 Ready** on `noodle.reminders`. Start Notifications with `./scripts/moodle-demo start notifications`.
3. Open Mailpit and show exactly two messages for **Pending essay**, one each for `alex@example.test` and `casey@example.test`. Open a message and follow its Moodle assignment link.
4. Run `./scripts/moodle-demo poll` again. Check `./scripts/moodle-demo logs --tail=30 notifications` for two `duplicate_reminder` entries. The queue drains and Mailpit remains at two messages.

### Optional SMTP retry scene

Use the first delivery in a fresh instance. After queueing the two reminders and before starting Notifications, enable Mailpit's temporary `451` SMTP response. Run the log command in one terminal and keep the final `curl` command ready in a second terminal. Restore SMTP after `notification_delivery_retry` appears, within the 20-second retry delay.

```sh
curl -fsS -X PUT http://localhost:18025/api/v1/chaos \
  -H 'Content-Type: application/json' -d '{"Sender":{"ErrorCode":451,"Probability":100}}'
./scripts/moodle-demo start notifications
./scripts/moodle-demo logs -f notifications
```

```sh
curl -fsS -X PUT http://localhost:18025/api/v1/chaos \
  -H 'Content-Type: application/json' -d '{}'
```

Show `notification_delivered` in the logs and two captured emails. The overlay lengthens the existing bounded SMTP retry delay for recording.

The demo uses visible individual assignments, standard student roles, and shared deadlines. Individual or group deadline overrides, specialized access rules, and Moodle cron are outside this local demonstration. The standard Compose deployment remains available through `compose.yaml`.
